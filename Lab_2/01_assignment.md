# Лабораторная работа № 2
## Методы оптимизации: SciPy, Optuna и проверяемое использование LLM

Версия комплекта: 1.0. Работа индивидуальная. Срок и способ распределения рецензий преподаватель сообщает отдельно. Требования этого документа имеют приоритет над рекомендациями LLM и примерами из прошлогодних материалов.

## 1. Цель
Освоить постановку и численное решение задач условной оптимизации; сравнить локальный и глобальный поиск, явные ограничения и штрафы; научиться проверять предложения LLM и воспроизводимо представлять результаты. Не требуется разработка собственного оптимизатора, настройка оптимизаторов через вложенную Optuna или использование платной модели.

## 2. Постановка
Найти минимум и максимум функции

$$f_a(x,y)=x^2+y^2+a[2-\cos(4x)-\cos(4y)]$$

в области

$$x\le2,\qquad y\le3,\qquad x+y\ge0.5.$$

Все переменные и значения функции в этой учебной задаче безразмерны; аргументы косинуса — в радианах. Основное значение $a=1$, контрольное $a=0$. Область — замкнутый треугольник; охватывающий прямоугольник $[-2.5,2]\times[-1.5,3]$ выводится из ограничений, а не вводит новую физическую границу.

1. Выведите вершины области. Объясните существование глобальных экстремумов.
2. При $a=0$ найдите экстремумы аналитически, сопоставьте с вычислениями.
3. Объясните, что изменится при замене $y\le3$ на $y<3$.
4. При $a=1$ постройте предварительную карту функции. Не называйте минимум сетки доказанным точным глобальным минимумом.
5. Приведите градиент функции, проверьте его численным дифференцированием в нескольких точках; объясните различия локального и глобального поиска.

Нельзя незаметно менять область, функцию, направление неравенств или коэффициент a.

## 3. Общий вычислительный контракт
Для сравнения используйте минимизируемую цель $J_s=s f_a$, где $s=+1$ для поиска минимума исходной функции, $s=-1$ для максимума. В журнале сохраняйте именно исходную $f_a$, знак s и фактически оптимизируемую цель отдельно.

Нормированные остатки:

$$g_1=(x-2)/4.5,\quad g_2=(y-3)/4.5,\quad g_3=(0.5-x-y)/9.$$

Допустимость по численному допуску: $v=\max(0,g_1,g_2,g_3)\le10^{-6}$. Это численная проверка исходных ограничений, а не изменение математической области. Сохраняйте остатки без округления, величину v и признак допустимости. Дополнительно показывайте реальные координаты и исходные неравенства лучших точек.

Для штрафной постановки:

$$P=\sum_{i=1}^3\max(0,g_i)^2,\qquad F_s=s f_a+\rho P.$$

Основной коэффициент $\rho=100$; исследование чувствительности — $\rho\in\{1,10,100\}$. Коэффициенты не подбираются задним числом по каждому методу. При конечном rho минимум F не обязан быть допустимым! Фиксированная нормировка облегчает сравнение, но не даёт гарантии превосходства всех допустимых точек над всеми недопустимыми.

## 4. Обязательные методы

| Код | Реализация | Ограничения |
|---|---|---|
| SLSQP-C | `scipy.optimize.minimize`, `method='SLSQP'` | Bounds охватывающего прямоугольника и явное неравенство x+y>=0.5; градиент аналитический |
| DE-C | `scipy.optimize.differential_evolution` | те же Bounds и явное линейное ограничение через LinearConstraint |
| SLSQP-P | SLSQP | только Bounds; неравенство x+y>=0.5 учитывается общей штрафной функцией; аналитический градиент штрафованной цели |
| TPE-P | Optuna, TPESampler | равномерные непрерывные suggest_float для x,y в Bounds; та же штрафная цель |

Для явных ограничений допускается передать все три неравенства; неравенства, дублирующие Bounds, объясните. В SLSQP-P оставление x+y>=0.5 как явного ограничения лишает опыт смысла. Первые два штрафных вклада внутри Bounds нулевые — это намеренно: используются общий вектор проверок и одинаковая область поиска.

DE-C: `popsize=15`, `maxiter=10000`, `tol=0`, `atol=0`, `polish=False`, `workers=1`, `updating='immediate'`. Ограничитель числа вычислений из раздела 5 обязателен: maxiter сам по себе бюджетом не является.

SLSQP: `maxiter=10000`, `ftol=1e-9`. Неуспех или ранняя остановка сохраняются, а не скрываются увеличением числа рестартов.

TPE-P: `n_startup_trials=20`, последовательный режим `n_jobs=1`, без pruning. Один trial — одно вычисление F в выбранной точке; не запускайте внутри trial другой оптимизатор. Достаточно обычного TPESampler без дополнительных экспериментальных опций.

## 5. Протокол эксперимента и бюджет
Для каждого независимого запуска потолок B=600 фактических скалярных вычислений f. Все внутренние вызовы цели, включая повторные точки и пробы производных, если они вычисляют f, учитываются. Аналитическое вычисление градиента без вычисления f не расходует этот счётчик; число вызовов градиента сохраняется отдельно.

Перед следующим вызовом f при уже исчерпанном B остановите поиск контролируемым исключением либо эквивалентным механизмом. Не возвращайте фиктивное «плохое значение» вместо остановки. Сохраните выполненную историю, даже если библиотека не вернула итоговый объект. Достижение бюджета — самостоятельный штатный статус эксперимента. Методы могут завершиться раньше B: равный потолок не означает равную фактическую стоимость. Не дополняйте короткий запуск повторением одной точки.

Для DE число проверок дешёвых ограничений может быть больше числа вызовов f; это не ошибка. Время и число проверок ограничений при наличии учитываются отдельно. Безопасностный предел maxiter также может завершить запуск раньше B.

Основной эксперимент при a=1: оба направления, четыре метода, пять run_id:

| run_id | seed (DE/TPE) | старт (SLSQP-C/SLSQP-P) |
|---|---:|---|
| 1 | 11 | (-1, 2) |
| 2 | 23 | (0.25, 0.25) |
| 3 | 37 | (1.5, 2.5) |
| 4 | 51 | (-2, 2.75) |
| 5 | 71 | (1, -0.25) |

Итого 40 основных запусков. Локальные пять стартов — исследование чувствительности к старту, а не пять случайных независимых реализаций одного процесса. Стохастические пять seeds — независимые повторы в рамках выбранного протокола. Не объединяйте пять запусков в один поиск с бюджетом 600.

Исследование штрафа: для SLSQP-P добавьте rho=1 и rho=10 для обоих направлений и тех же пяти стартов (ещё 20 запусков). Rho=100 переиспользуйте из основного опыта. Для TPE исследовать все rho необязательно.

Контроль a=0: достаточно по одному запуску каждого основного метода в каждом направлении с run_id=1 (8 запусков, тот же B и основной rho). Если стохастический метод не достиг аналитического ответа, честно покажите ошибку: это не обязательно дефект реализации. Корректность арифметики проверяется также подстановкой аналитических точек.

Все библиотечные настройки, версии, seeds и старты сохраняйте в config.json. Параллельность и кэш цели отключить. Графическая сетка, проверка градиента, аналитические контрольные подстановки и иные диагностические вычисления выполняются отдельно и не включаются в историю оптимизатора; укажите их назначение. Не стройте сетку 10000×10000: достаточно 200–500 узлов на ось.

## 6. Что считать результатом
Сохраняйте две разные сущности:
1. рекомендацию оптимизатора (если получена), её исходную f, цель и нарушения;
2. лучшую допустимую точку среди ВСЕХ реальных вычислений f данного запуска.

Сравнивайте методы по второй сущности и её исходной f, а не по разным штрафованным целям. Если допустимых вычислений нет, результат — «не найдено», не ноль и не ближайшая недопустимая точка. Доля запусков, нашедших допустимую точку, не равна доле достижения глобального оптимума. Полезно отдельно оценить достижение контрольного качества при явно указанном пороге.

Изучите кривую лучшего допустимого значения от номера вычисления f; до первой допустимой точки значение отсутствует. Раннюю остановку показывайте с фактическим концом кривой. Не сравнивайте максимум исходной f с минимумом F без преобразования знака. Между группами C и P меняется не только алгоритм, но и способ учёта ограничений: общий итог относится к связке «метод + постановка». Для более чистого сравнения алгоритмов сопоставляйте SLSQP-C с DE-C и SLSQP-P с TPE-P; влияние постановки видно при сравнении двух SLSQP.

Все точки вычислений и принятые итерации SLSQP — разные истории. Записывайте копии координат, а не ссылки на изменяемый массив. Для DE/TPE не выдавайте облако проб за траекторию одного локального спуска.

## 7. Журналы и таблицы
Минимальный состав `results/`:

- `config.json`: задача, допуски, бюджеты, настройки и версии Python/numpy/scipy/optuna, список запусков и сведения о среде;
- `evaluations.csv`: run_key, phase (control/main/penalty), method, direction, a, rho (пусто для C), run_id, seed (если применим), eval_id с 1, x, y, f_raw, objective, g1, g2, g3, violation, penalty, feasible, elapsed_s;
- `runs.csv`: тот же идентификатор запуска, настройки, n_eval, n_grad (если применим), elapsed_s, stop_reason, optimizer_success (если доступен), message, координаты/значения рекомендации и лучшей допустимой точки, best_eval_id. Отсутствующие значения обозначайте пустым полем с объяснением, не фиктивным числом;
- отдельная история итераций SLSQP с номерами вычислений на момент callback (можно iterations.csv).

run_key уникален с учётом фазы, направления, метода, a, rho и run_id. Исследование rho=100 ссылается на main, не дублируется как новый запуск. Порядок строк и точность хранения должны позволять пересоздать таблицы и графики; сравнение границ делается до округления.

## 10. Воспроизводимость и сдача
Один ZIP с обычными относительными путями и одной корневой папкой:

```text
lab2_<Фамилия>/
  pyproject.toml
  uv.lock
  main.py
  report.md
  report.pdf
  figures/
  results/
  changes.md       # только при исправленной сдаче
```

Дополнительные собственные модули и конфиги разрешены. Не вкладывайте .venv, ключи, кэши, полные LLM-логи и гигантские notebook outputs. Ноутбук допустим как дополнение, не как единственная реализация.

Обязательные команды:

```bash
uv sync --frozen
uv run python main.py check
uv run python main.py run
uv run python main.py report
```

`check` проверяет формулы, градиент, знак цели, штраф и счётчик бюджета на маленьком синтетическом примере; не запускает полный опыт. `run` воспроизводит все обязательные опыты и сохраняет журналы. `report` читает результаты и пересоздаёт ВСЕ таблицы-артефакты и рисунки без нового поиска и без вызова LLM/API. Запуск report не обязан переписывать авторский аналитический текст report.md; все численные сводки текста должны соответствовать журналам. Сборку PDF выполняет студент своим инструментом; автоматизация компиляции не обязательна. Команды не требуют ручного ввода или абсолютных путей. Повторный run не смешивает старую и новую историю; выбранное поведение опишите. Эксперименты не должны обращаться к LLM API: LLM помогает разработке, а не вычисляет f.

Оформление: [профиль ГОСТ](02_gost_profile.md). Структура: [шаблон отчёта](05_report_template.md). Оценивание: [рубрика](03_grading_rubric.md). Перед сдачей: [чек-лист](07_submission_checklist.md).

Тема письма обязательно содержит «СМ6»; рекомендуемый вид: «СМ6 — ЛР2 — группа — Фамилия». Взаимное ревью — по [форме](04_peer_review_form.md); только преподаватель принимает решение об оценке. После отзыва отправляйте полный исправленный архив и changes.md с ответами на замечания.

## 11. Границы работы
Не требуются баллистическая оптимизация, кластер, нейросеть-суррогат, собственный решатель, nested optimization, pruning одного скалярного trial или доказательство обязательной победы TPE. Дополнительный RandomSampler или иной метод допустим после выполнения ядра и в отдельно обозначенном эксперименте.

Источники: методические материалы курса; документация scipy.optimize.minimize/SLSQP, differential_evolution, LinearConstraint; документация Optuna TPESampler; использованная документация по оформлению. Приводите конкретные страницы, фактические версии и даты обращения. Названия функций и настройки сверяйте с документацией зафиксированных версий.
